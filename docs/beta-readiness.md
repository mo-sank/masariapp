# Beta Readiness — Masari

Setup guide and checklist for the closed beta. Covers requirement **9.1** (preview
build distributed through TestFlight on iOS and internal testing on Android via
the EAS `preview` profile), **9.2** (the readiness checklist the team signs off
before inviting testers), and **9.3** (recording timed lesson completion and
first-trade behavior for at least 5 teens).

> Expo SDK 57 (`expo ~57.0.26`). This project does **not** use Bun (no
> `bun.lock`), so EAS CLI runs as `npx eas-cli@latest`. Native projects are
> generated by Continuous Native Generation — configure native behavior in
> `app.json` / `app.config.ts` / `plugins/`, never by hand-editing `ios/` or
> `android/`.

## 1. Environment variables for the preview build

The app reads only `EXPO_PUBLIC_*` values at build time (they are inlined into
the JS bundle, so **public values only — never a secret**). Confirm these are set
for the `preview` environment in EAS:

| Variable | Purpose |
| --- | --- |
| `EXPO_PUBLIC_AUTH0_DOMAIN` | Auth0 tenant domain (also consumed by the native Auth0 config plugin at build time). |
| `EXPO_PUBLIC_AUTH0_CLIENT_ID` | Auth0 native app client id. |
| `EXPO_PUBLIC_AUTH0_AUDIENCE` | Auth0 API audience. |
| `EXPO_PUBLIC_SUPABASE_URL` | Supabase project URL. |
| `EXPO_PUBLIC_SUPABASE_ANON_KEY` | Supabase publishable anon key. |
| `EXPO_PUBLIC_LEGAL_PRIVACY_URL` | **Must be the live Privacy Policy URL** for beta (defaults to a placeholder otherwise). |
| `EXPO_PUBLIC_LEGAL_TERMS_URL` | **Must be the live Terms URL** for beta. |
| `EXPO_PUBLIC_SENTRY_DSN` | Public Sentry DSN (optional; enables crash reporting). |

Build-time **secrets** (never `EXPO_PUBLIC_`, never committed) that belong in the
EAS build environment:

| Secret | Purpose |
| --- | --- |
| `SENTRY_AUTH_TOKEN` | Lets the Sentry Expo plugin upload source maps during the build. |

> Server-only secrets (`MARKET_DATA_API_KEY`, the Auth0 Management credentials,
> `CRON_SECRET`, the Supabase service-role key) are **Supabase Edge Function
> secrets** and must never appear in the app, in `.env.example`, or in the EAS
> build env.

## 2. Create the EAS preview build (requirement 9.1)

The `preview` profile in `eas.json` is **store-distribution** so the artifacts
are submittable to TestFlight (iOS `.ipa`) and the Play internal-testing track
(Android `.aab`). `appVersionSource` is `remote` and `autoIncrement` is on, so
EAS bumps the build number for each build.

```bash
# iOS — produces a store-signed .ipa for TestFlight
npx eas-cli@latest build --platform ios --profile preview

# Android — produces an .aab for the Play internal-testing track
npx eas-cli@latest build --platform android --profile preview

# Or both at once
npx eas-cli@latest build --platform all --profile preview
```

Need a quick **direct-install** build for a device on hand instead of going
through the stores? Use the `preview:adhoc` profile (iOS ad hoc, Android APK —
installable from the EAS build URL, no store review):

```bash
npx eas-cli@latest build --platform all --profile preview:adhoc
# iOS ad hoc first needs the device registered:
npx eas-cli@latest device:create
```

### Submit to the testing tracks

```bash
# iOS → TestFlight (adds the build to the "Beta Testers" group from eas.json)
npx eas-cli@latest submit --platform ios --profile preview --latest

# Android → Play Console internal testing track
npx eas-cli@latest submit --platform android --profile preview --latest
```

- [ ] iOS preview build succeeded and uploaded to TestFlight.
- [ ] Build processed in App Store Connect and assigned to the `Beta Testers`
      internal group.
- [ ] Android preview build succeeded and uploaded to the Play internal track.
- [ ] Internal testers accepted the Play opt-in link and installed.
- [ ] Beta testers invited (TestFlight invite + Play internal opt-in URL).

### Over-the-air updates (optional during beta)

Both store and ad hoc preview builds listen on the `preview` channel, so you can
push a JS-only fix without a new native build:

```bash
npx eas-cli@latest update --branch preview --message "beta fix: <summary>"
```

## 3. Beta Readiness checklist — sign off before inviting testers (requirement 9.2)

### Legal & consent

- [ ] **Privacy Policy is live** and `EXPO_PUBLIC_LEGAL_PRIVACY_URL` points to it
      (not the dev placeholder). Open Settings → Privacy in the build and confirm
      the real page loads.
- [ ] **Terms are live** and `EXPO_PUBLIC_LEGAL_TERMS_URL` points to them. Confirm
      Settings → Terms opens the real page.
- [ ] **Age gate** works: under-13 is blocked at onboarding (`create_profile`
      rejects age < 13).
- [ ] Parental/guardian consent process for teen testers is in place per your
      research protocol (collected **outside** the app).

### Account deletion (data rights)

- [ ] **Account deletion works end to end.** In the build: Settings → Delete
      account → confirm. Verify the Supabase `profiles` row is gone (cascades
      remove the user's data) and the Auth0 user is removed by the
      `delete-account` Edge Function. Re-login should require a fresh sign-up.

### Disclaimers

- [ ] The persistent disclaimer **"Paper money. Educational only. Not financial
      advice."** appears on every price/trade screen (order ticket, order
      confirmation, guided-trade step) — it is rendered by the shared
      `Disclaimer` component so the wording is identical everywhere.
- [ ] Portfolio carries the "Paper money" tag.

### No secrets in the bundle

- [ ] Only `EXPO_PUBLIC_*` client values are present; no service-role key, no
      market-data key, no Auth0 Management credentials.
- [ ] Spot-check the built bundle for leaked secrets, e.g.:

      ```bash
      # Export the production JS bundle and grep for secret-looking strings
      npx expo export --platform ios --output-dir /tmp/masari-bundle
      grep -RniE "service_role|secret|BEGIN (RSA|PRIVATE)|mgmt|management" /tmp/masari-bundle || echo "no obvious secrets"
      rm -rf /tmp/masari-bundle
      ```

### Analytics & privacy

Analytics is an allowlist-only, PII-stripped queue (`src/lib/analytics.ts`,
allowlist in `src/features/progress/analytics-events.ts`; the `log_events` RPC
enforces the same allowlist server-side). Confirm:

- [ ] Only allowlisted event names are ever sent. Current allowlist:
      `session_start`, `onboarding_completed`, `lesson_started`, `step_answered`,
      `lesson_completed`, `rewind_session_completed`, `trade_placed`,
      `reflection_submitted`, `watchlist_changed`, `stock_viewed`.
- [ ] No free text, email, or token is attached to any event (the prop-key
      denylist drops `email` / `token` / text).
- [ ] A short beta run shows events flushing to `log_events` (and retrying when
      offline rather than dropping).

### Build health (run these in-repo — see §5)

- [ ] `npx expo-doctor` passes.
- [ ] `npx expo lint` passes.
- [ ] `npx tsc --noEmit` passes.
- [ ] Jest suite passes (`npm test`).

### Crash reporting

- [ ] Sentry DSN set for preview; `SENTRY_AUTH_TOKEN` set in the EAS build env so
      source maps upload and crashes symbolicate.

events, so timings can be cross-checked later with the evaluation queries in
`docs/evaluation-queries.sql` (median lesson duration, first-trade rate within
24h).

## 6. Human-only / cloud steps that remain (cannot be automated here)

An automated agent prepared the build config and this checklist but **cannot**
perform the following — the team must do them manually with real credentials and
devices:

1. Run `eas build --profile preview` against the real Expo/Apple/Google accounts.
2. Upload to TestFlight and the Play internal-testing track (`eas submit`) and
   invite testers.
3. Verify Privacy Policy and Terms are hosted live and set the two
   `EXPO_PUBLIC_LEGAL_*` URLs to them.
4. Verify account deletion on a real device against the live backend.
5. Recruit and obtain guardian consent for ≥ 5 teen testers.
6. Run the live sessions and fill in the timing notes in §4. **Do not fabricate
   session data** — these numbers feed the evaluation report.
